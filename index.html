The problem

Local setup is guesswork spread across forum posts.

You need to know how much VRAM your card has, which model fits in it, which parameters to change for speed, and what an opaque llama-server error actually means. This toolkit replaces each of those guesses with something you can read off your own machine.

The dashboard

Four tabs, in the order you use them

01 System

Know the machine first

A full hardware scan: processor, memory modules, graphics cards with their VRAM, disks with usage bars. Start here — the VRAM figure decides which models you can actually load. The result is cached, so you wait once.

02 Ollama

Control the runtime

Installation state and the server process in one place: start it, stop it, read its version, run an installer already on the machine. When the Windows desktop app restarts the server behind your back, the page says so instead of claiming a stop that did not stick.

03 Models

Everything a model needs

The installed list and the in-memory list, with info, load, stop and remove on every row. Below them, forms to run a single prompt, register a local GGUF file, and create a configured copy of a model — a new model on disk, with the original untouched.

04 Benchmark

Stop guessing at parameters

Pick a model and a set of prompts, define several parameter sets, run them all. Build a configuration by hand from 23 Ollama options, or drop in a JSON file. Every configuration runs every prompt, and the model is preloaded before each one so load time never lands in the timings.

The headline feature

A comparison, not an opinion

The other tabs bring convenience. This one gives you a number you would otherwise have to guess at.

The verdict comes first: which configuration generated fastest, and by how much over the runner-up. Then output speed, prompt speed and response time, each scaled against the best value in its own group, followed by a summary table and per-prompt detail.

A run takes minutes, so it happens in a background thread on the server — reloading the browser does not lose it. Only one comparison runs at a time, because two would contend for the same GPU and make every timing in both meaningless.

What makes the numbers usable: fix the seed and change one option at a time. If two configurations differ in several places, you cannot attribute the difference to any one of them.

Setup

Four commands and it runs

Python 3.10 or newer, plus Git to fetch the core submodule.

  1. 1 Clone with the submodule

    bash 
    git clone --recurse-submodules https://github.com/ModelSetupHub/gui.git
cd gui

  2. 2 Create a virtual environment

    bash 
    python -m venv .venv
.venv\Scripts\activate

  3. 3 Install core, then the web dependencies

    bash 
    pip install -e ./core
pip install -r requirements.txt

  4. 4 Run it

    bash 
    python app.py

Then open http://127.0.0.1:5000/

Do not skip the first line of step 3

core is a submodule, not a copy of the code. Without pip install -e ./core every request fails with ModuleNotFoundError: No module named 'core'.

Before you install

Three limits, stated up front

  • ◆ Windows only, for now

    The hardware scanner is built on PowerShell and WMI, so the System tab does not work anywhere else yet.

  • ◆ No authentication

    The dashboard is a local server with no auth, and its endpoints start Ollama, load and remove models, and run installers on the host. Keep it on localhost — it is not built to sit on a network.

  • ◆ Ollama is required

    Everything except the System tab needs Ollama installed on the machine.
